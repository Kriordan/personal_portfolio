## Objective

Implement and validate JWT-based API authentication (`login`, `refresh`, `signup`) while preserving existing Flask-Login session auth behavior for the web app.

## Scope Delivered

- Added explicit JWT token lifetimes in `project/_config.py`:
  - `JWT_ACCESS_TOKEN_EXPIRES = 15 minutes`
  - `JWT_REFRESH_TOKEN_EXPIRES = 30 days`
- Added API auth integration tests in `tests/test_api_auth.py` covering:
  - successful JWT login for verified users
  - rejection for unverified users
  - refresh token exchange for new access token
  - invite-based signup flow
  - separation of JWT auth from Flask-Login session cookies
- Fixed invitation expiry comparison in `project/models.py` to handle timezone-naive datetimes safely in environments like SQLite-backed tests.

## Legacy Behavior Ported

- Existing Flask-Login session auth remains unchanged for the web/Jinja routes (`project/account/views.py`).
- API auth remains token-based and does not set Flask-Login session state (`_user_id`), preserving the "session for web, JWT for API" split.

## Architecture and Design Choices

### 1) Keep dual auth systems side-by-side
- What was done: validated JWT endpoints through API tests while checking session separation behavior.
- Why this approach was chosen: mobile/API clients need stateless bearer tokens, while existing web views rely on Flask-Login sessions.
- Trade-offs considered: unifying auth now would increase migration risk; dual mode allows incremental rollout.
- Key implementation details: `tests/test_api_auth.py` asserts JWT login success and confirms no Flask-Login session key is created.

### 2) Configure explicit token lifetimes
- What was done: set JWT expirations in app config.
- Why this approach was chosen: aligns runtime behavior with intended security model and mobile refresh flow.
- Trade-offs considered: shorter access token increases refresh traffic, but reduces exposure window for leaked tokens.
- Key implementation details: `project/_config.py` now sets 15-minute access and 30-day refresh expirations.

### 3) Normalize invitation expiry timezone handling
- What was done: guarded `InvitationMixin.is_expired` against naive datetime objects.
- Why this approach was chosen: test and local DB backends may deserialize timezone-aware columns as naive values.
- Trade-offs considered: coercing naive values to UTC assumes stored values are UTC; this matches current app defaults and avoids runtime crashes.
- Key implementation details: `project/models.py` now coerces `expires_at` with `replace(tzinfo=timezone.utc)` when needed.

## API Contract

- `POST /api/v1/auth/login`
  - Request: `{ "email": string, "password": string }`
  - Success `200`: `{ "access_token": string, "refresh_token": string, "user": { ... } }`
  - Failure: `401` invalid credentials, `403` unverified email
- `POST /api/v1/auth/refresh`
  - Auth: `Authorization: Bearer <refresh_token>`
  - Success `200`: `{ "access_token": string }`
- `POST /api/v1/auth/signup/<token>`
  - Request: `{ "email": string, "username": string, "password": string }`
  - Success `201`: `{ "message": "Account created.", "user": { ... } }`
  - Failure: `404` invalid invite, `410` expired invite, `409` used invite/duplicate account
